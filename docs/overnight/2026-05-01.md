## Research Findings

### Django Updates & Deprecations
- **`USE_L10N = True` in `MetaGap/MetaGap/settings.py:138` is dead.** Django 5.0 *removed* the setting outright (see Django deprecation timeline). Django 5.1.1 silently ignores it; once any plugin or test calls `from django.conf import settings; settings.USE_L10N`, behaviour will be unaffected, but the line is misleading and will produce `RemovedInDjango50Warning`-style noise on older code paths. Drop it.
- **`python manage.py check --deploy` (DEBUG=0)** reports 5 warnings:
  - `security.W004` — `SECURE_HSTS_SECONDS` not set
  - `security.W008` — `SECURE_SSL_REDIRECT` not set
  - `security.W009` — `SECRET_KEY` < 50 chars / low entropy / `dev-secret` default would be used if `SECRET_KEY` env var is unset in production
  - `security.W012` — `SESSION_COOKIE_SECURE` not set
  - `security.W016` — `CSRF_COOKIE_SECURE` not set
  None of these block dev-mode work, but together they describe a deployment that would ship session cookies in cleartext with no HSTS preload protection. Lock them behind `if not DEBUG:` blocks (or behind an env flag) so CI's `check --deploy` step (which doesn't currently exist — see CI Gaps) goes green for production builds.
- **Django 5.2 LTS migration window is open.** 5.2 stays in mainstream support until Apr 2028 and security-only through Apr 2029. The project should treat the 5.1.1 → 5.2.x bump as the next planned upgrade and defer 5.2 → 6.0 until 6.x is quieter (6.0.4 itself is still patching CVEs monthly).

## Suggestions
Ranked by value-to-effort ratio.

1. **Migrate the 170 pytest-style functions to `unittest.TestCase` — or add `pytest -q` to CI.** Single biggest leverage. Either path will likely reveal latent failures (notably `test_vcf_database.py` references nonexistent model fields). Pair with deletion of the now-redundant pytest helpers.
2. **Delete dead code from `app/services/vcf_database.py` (`get_or_create_sample_group`, the four `extract_*` helpers, `convert_to_python_type`)** and the empty `test_import_data_view.py`. Pure subtraction; reduces audit surface.
3. **Drop `requests`, `beautifulsoup4`, `docutils`, and their transitives from `requirements.txt`.** Removes urllib3 CVE-2026-21441 exposure with zero code change. Re-pin only if a future feature legitimately needs them.
4. **Bump Django to 5.2.13 (LTS).** Six 2026 CVEs in one go and aligns with a 3-year support window. Run the test suite plus a fresh `pytest` on a feature branch first.
5. **Add a production-hardening block to `settings.py`** guarded by `if not DEBUG:` — `SECURE_SSL_REDIRECT = True`, `SESSION_COOKIE_SECURE = True`, `CSRF_COOKIE_SECURE = True`, `SECURE_HSTS_SECONDS = 31536000`, `SECURE_HSTS_INCLUDE_SUBDOMAINS = True`, `SECURE_HSTS_PRELOAD = True`. Add `python manage.py check --deploy` to CI to keep the warnings from regressing.
6. **Remove `USE_L10N = True` (line 138) from `settings.py`.** Setting was deleted in Django 5.0; line is dead config noise. Same edit can clean up the historical `Django 2.1.2` comments at the top of the file.
7. **Pick one source of truth for metadata maps** — delete the duplicate Python constants in `vcf_metadata.py:183-366` and have `vcf_file_utils.py` use `load_metadata_configuration()` like the rest of the importer. Avoids the `buildname`/`buildversion` drift becoming a real bug.
8. **Add `pip-audit` + `ruff` + `manage.py check --deploy` to CI**, plus `actions/setup-python@v5 cache: 'pip'`. ~15 lines of YAML, catches the next urllib3-style CVE automatically and shaves ~30–60 s off every CI run.
9. **Delete or `.gitignore` `MetaGap/MetaGap/settings.py.orig` and decide what to do with `MetaGap/_po_count.py`.** Working-tree hygiene; tiny.
10. **Resolve the 3 newly-untranslated Russian strings** (`app/locale/ru/LC_MESSAGES/django.po`). Run `makemessages -l ru` to list them, then translate.
