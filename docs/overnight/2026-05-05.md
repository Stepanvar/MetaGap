## Research Findings

### Django Updates & Deprecations

Relevant for this codebase if/when bumping to 5.2 LTS:

- **`CompositePrimaryKey`** (5.2 new): could replace the awkward composite
  uniqueness on `AlleleFrequency(sample_group, chrom, pos, ref, alt)` if a
  surrogate PK is ever undesirable for a future variant table.
- **MySQL default `utf8mb4`** (5.2): no impact, project uses SQLite by default.
- **PostgreSQL 14+ minimum** (5.2): note for prod deploys.
- **`method_decorator()` async support** (5.2): no async views in current
  code — not relevant yet.
- **Deprecations affecting this code**:
  - `django.contrib.staticfiles.finders.find(all=...)` → `find_all=...`. Check
    if any direct call sites exist (none found in a quick grep).
  - `request.user`/`request.auser()` fallback in
    `django.contrib.auth.login()` deprecated when `user is None` — current
    `app/views.py` does not pass `None`, so safe.
  - PostgreSQL aggregate `ordering=` keyword deprecated → `order_by=`. No
    PG-specific aggregates currently used.

### VCF / Genomics Horizon

- **VCF 4.5** spec is published (last modified 2024-10-09 on
  `samtools/hts-specs`) and adds modified-base information at the genotype
  level. The codebase advertises `##fileformat=VCFv4.2` everywhere in test
  fixtures — consider extending `VCFMetadataParser` to recognize 4.4/4.5
  header conventions, especially the modified-base `MM`/`ML`-style annotations
  if downstream methylation work is in scope.
- Governance note: the spec is now under GA4GH / hts-specs (not 1000 Genomes)
  — the canonical URL for any future doc references is
  `samtools.github.io/hts-specs/`.
- **pysam 0.23.x** wraps htslib 1.21 with improved I/O exceptions; bumping
  would surface clearer error strings for the
  `_should_retry_with_inflated_copy` substring matcher (worth re-validating
  the `"bgzf"`/`"bgzip"` heuristic against newer htslib messages before
  bumping).

### CI Gaps

`.github/workflows/ci.yml` (92 lines) checks tests + coverage and uploads
artifacts. Gaps:

1. **No linter / formatter step.** `ruff`, `flake8`, or `black --check` would
   catch issues like the dead double-cleanup branch in `vcf_importer.py:110-112`
   before merge.
2. **No type checker.** The codebase already uses comprehensive `typing`
   imports; running `mypy --strict app/services/` would have low integration
   cost.
3. **No dependency security scan.** Add `pip-audit` or `safety check` —
   current Django 5.1.1 + django-allauth 65.0.1 versions would both fail.
4. **No matrix.** Runs only on Python 3.11; pinning the latest patch
   release (3.11.x) and adding 3.12 would catch incompatibilities early.
5. **Dead annotator step.** Lines 65-76 grep `test-output.log` for
   `"Unhandled metadata key"` and emit `::warning::`, but **no module in the
   codebase emits that exact string** (verified via repo-wide grep). Either
   wire up the warning at its intended emission site (likely
   `app/services/vcf_metadata.py`'s parser warnings list) or drop the step.
6. **`coverage` is not pinned** in `requirements.txt`; CI does
   `pip install -r requirements.txt coverage` which floats the version. A
   coverage tool bump could change report formatting and silently break the
   `--fail-under` enforcement.
7. **Pull-request branch list is open** (`pull_request:` with no `branches`),
   while `push` is gated to `main`. Consistent — fine — but the workflow
   never runs `compilemessages`, so a broken `.po` would land silently and
   fail at `AppConfig.ready()` runtime. Add a step:
   `cd MetaGap && DJANGO_SETTINGS_MODULE=MetaGap.settings django-admin compilemessages`.

## Suggestions

Ranked by estimated value (security first, then maintainability, then niceties):

1. **Bump Django 5.1.1 → 5.2.13 LTS** and pin in `requirements.txt`. 5.1 is
   past extended support and three known security releases have shipped
   since the pinned version; one is a SQLi (`QuerySet.order_by` with
   `FilteredRelation`) that any installed Django 5.1 application is exposed
   to regardless of feature usage.
2. **Bump django-allauth 65.0.1 → 65.16.0**. The 65.14.x line patches a
   SAML open-redirect, an email-verification flaw, and an X-Forwarded-For
   rate-limit-bypass. Even with SAML disabled and `ACCOUNT_CHANGE_EMAIL=False`,
   the rate-limit fix is broadly relevant.
3. **Convert orphan pytest-style tests** in
   `test_vcf_database.py`, `test_filters.py`, `test_filters_additional.py`,
   `test_locale_compiler.py` to `TestCase` subclasses (or wire `pytest-django`
   into the runner). 170+ assertions currently provide zero coverage. Same
   recommendation as 2026-05-04 and 2026-05-03 — still not done.
4. **Add `pip-audit` (or `safety`) step to CI**. Would have flagged the
   above two upgrades automatically and ratcheted future drift.
5. **Add a lint step (`ruff check`) and a type-check step
   (`mypy --strict app/services/`) to `ci.yml`.** Low-cost, catches the dead
   `cleanup_pysam_sample_group()` branch and similar latent issues.
6. **Remove or wire up the dead "Unhandled metadata key" annotator** in
   `ci.yml:65-76`. Either emit that exact string from
   `vcf_metadata.py`'s parser warnings, or drop the CI step — currently it
   is muscle memory in the workflow file.
7. **Pin `coverage` in `requirements.txt`** so local + CI runs match exactly,
   and so the `--fail-under` thresholds aren't dependent on a floating
   tooling version.
8. **Add `compilemessages` to CI** as a separate step. The app currently
   compiles `.po` lazily in `AppConfig.ready()`, meaning a broken catalog
   would only surface on container start — a CI step takes seconds and
   prevents production breakage. While there, fix the 3 untranslated
   Russian strings in `app/locale/ru/.../django.po` and the 2 untranslated
   English strings in the project-level `MetaGap/locale/en/.../django.po`.
