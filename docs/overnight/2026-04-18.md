Four test modules in `app/tests/` declare `pytestmark = pytest.mark.django_db` and use top-level `def test_*` functions with `pytest.fixture` — a pattern that only runs under `pytest` with `pytest-django` installed:

- `requirements.txt` pins `pytest==8.4.2` but has **no `pytest-django`**.
- CI (`.github/workflows/ci.yml:36`) runs `python -m coverage run manage.py test` — unittest loader. Functions that are not `TestCase` subclasses are **silently skipped**.
- `conftest.py` (lines 27–41) defines `autouse` pytest session fixtures that Django's runner ignores.
- Net effect: coverage of `filters.py`, `vcf_database.py` helpers, and additional view paths is over-reported relative to CI expectations. The app/ 70% threshold could be inflated by dead tests that never actually ran — or (equally possible) under-reported because these files contribute zero coverage in the unittest path.

## Research Findings

### Django Updates & Deprecations

**Django 5.1.1 → 5.2.13 upgrade path (recommended LTS).** Low-risk for this codebase; 5.2 is supported through April 2028. `URLField` default scheme change (http → https) is a 6.0 removal, not 5.2. `FORMS_URLFIELD_ASSUME_HTTPS` transitional setting is removed in 6.0 only. The project uses `SampleGroup.delete(using, keep_parents)` with positional args (`app/models.py:595`); this is still valid because `Model.save`/`asave` positional-arg removal applies to those methods, not custom `delete` overrides.

**6.0-track features worth noting:** built-in CSP support (replaces `django-csp`), a first-party background tasks framework, `AsyncPaginator`/`AsyncPage`, modernized `email.message.EmailMessage`. None are adopted by this project yet; all are optional.

**Python support window:** Django 5.2.x is the last to support Python 3.10/3.11; 6.0 requires 3.12+. The project is pinned to 3.11, so 5.2 LTS is the natural destination. A move to 6.0 would require bumping Python.

### VCF/Genomics Horizon

- **VCF 4.5 draft** (hts-specs) adds modified-base information to genotype. Not a breaking change for existing 4.2/4.3 VCFs; the import pipeline is unaffected unless the project intends to ingest 4.5-specific annotations.
- **pysam 0.23.x** (htslib 1.21) supports the same VCF range as 0.22; upgrade is purely maintenance. `AlignedSegment.query_qualities_str` is BAM-oriented and not used by this project.
- **vcfpy 0.14.2** remains current; no 1.x on the horizon.

### CI Gaps

- **CI entrypoint runs only unittest.** `.github/workflows/ci.yml:36` invokes `python -m coverage run manage.py test`, so pytest-style test files (listed above) never execute. Either port those files to `TestCase` subclasses or add `pytest-django` and a separate pytest job — but don't leave them silently skipped.
- **No lint step.** No `ruff`, `flake8`, `black --check`, or `isort --check`. A simple `ruff check` job runs in seconds and would catch unused imports and trivial style issues (also surfaces the pytest tests' dead imports of nonexistent helpers).
- **No security scan.** No `pip-audit` or `bandit` step. Given Django 5.1.1 EOL, `pip-audit` would immediately flag 7–8 CVEs.
- **No compilemessages verification.** CI does not run `django-admin compilemessages`; a broken `.po` diff would ship without failure.
- **Branch mismatch (unchanged from prior reports).** Workflow triggers on `main`; repo is on `master`. Either rename the branch, change the workflow trigger, or add both (`on.push.branches: [main, master]`). Until fixed, no `master` push ever runs CI.
- **`coverage` install is not pinned.** CI installs `coverage` via `pip install -r requirements.txt coverage` with no version cap. Pinning avoids surprise behavior differences when `coverage` bumps.
