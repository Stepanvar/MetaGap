# Architecture and Logic

## Data Flow
The VCF data flow follows a structured pipeline starting with file upload through the web interface. When a user uploads a VCF file, the `ImportDataView` in `views.py` receives the file and passes it to the `VCFImporter`. The `VCFImporter` uses `VCFMetadataParser` to extract metadata from the VCF header sections, mapping them to Django models using the configuration in `metadata_fields.yaml`. The extracted metadata is processed and validated before creating a `SampleGroup` instance in the database. Concurrently, the VCF records are parsed and converted to `AlleleFrequency` instances, which are linked to the corresponding `SampleGroup`. The `VCFDatabaseWriter` handles the actual database persistence of both metadata and variant data.

## Data Schema
The core data schema centers around the `SampleGroup` model, which represents a collection of related samples with associated metadata. Each `SampleGroup` belongs to an `OrganizationProfile` and contains foreign key relationships to various specialized metadata models like `ReferenceGenomeBuild`, `SampleOrigin`, `MaterialType`, and sequencing platform-specific models (`IlluminaSeq`, `OntSeq`, etc.). The `AlleleFrequency` model stores the actual genetic variant data and links back to a `SampleGroup`, containing fields for chromosome, position, reference/alternative alleles, quality scores, and foreign keys to `Info` and `Format` models that store additional VCF-specific data.

## VCF Merging
The `MetagapUserCode` module provides a separate VCF merging workflow implemented in the `merge_vcf` package. This workflow includes command-line tools for combining multiple VCF files into a single cohort-level file. The `cli.py` module orchestrates the workflow, while `merging.py` handles the actual file combination. The `joint_call.sh` script provides a bash-based alternative approach using bcftools. The merging process includes steps for normalization, quality filtering (QUAL and AN thresholds), removal of sample-specific genotypes, and appending custom metadata headers. This functionality operates independently of the main Django application and can be invoked as a standalone tool.

## Configuration
Metadata mapping is controlled by `metadata_fields.yaml` located in `MetaGap/app/config/`. This YAML file defines four key mappings: `metadata_section_map` for normalizing header section names, `metadata_models` for binding sections to Django models, `metadata_field_aliases` for handling synonymous field names, and `section_primary_field` for determining which field represents a section's value. The `VCFMetadataParser` loads and validates this configuration file, caching the result for performance. The system normalizes metadata keys to snake_case and applies alias resolution to ensure consistent field mapping regardless of variations in VCF header naming conventions.
