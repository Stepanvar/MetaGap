## Research Findings

### Django Updates & Deprecations

- **Django 5.1 has been EOL since 2025-12-31**; no further security fixes. Django 5.2 LTS (supported through 2028-04) is the recommended landing point.
- **Django 5.2.13 / 6.0.4 / 4.2.30 (2026-04-07) ship four CVE-tier fixes**, of which the most directly relevant to this codebase is the `MultiPartParser` base64 + whitespace DoS. The MetaGap import endpoint accepts arbitrary user-uploaded multipart payloads, so this is exposed in production with the current pin. Other April-7 fixes: ASGI underscore-header normalization, ASGI `Content-Length` underflow bypassing upload-size limits, `GenericInlineModelAdmin` POST permission bypass, admin `list_editable` forged-POST instance creation. All low-to-medium severity but `5.1.1` is missing every patch.
- **Django 6.0 GA shipped 2025-12-03** (not LTS). Brings: Template Partials (`{% partialdef %}` / `{% partial %}`), built-in async **Tasks** framework (Celery alternative for many cases), native CSP support (no more middleware shim), modernized Email API, Python 3.12–3.14 support. Post-5.2 wins, not blockers.
- **`USE_L10N` was removed in Django 5.0** (deprecated in 4.0, removed in 5.0). The line `USE_L10N = True` at `MetaGap/MetaGap/settings.py:138` is therefore inert dead syntax on a 5.1 install — Django 5.x permanently treats `USE_L10N` as `True`. Delete the line as part of the Django bump.
- **Django 6.0 JSONField behavior changes** to know about for the eventual 6.0 jump:
  - `django.contrib.postgres.fields.JSONField` will be removed (a stub stays for historical migrations).
  - Querying a top-level `JSONField` value with `None` will compile to `IS NULL`; use `JSONNull` to match a JSON `null`. We use `JSONField` in `Info.additional`, `Format.payload`, `SampleGroup.additional_metadata`, `SequencingInstrument.additional_info`, `ReferenceGenomeBuild.additional_info`, `InputQuality.additional_metrics` — none use the deprecated string-literal pattern, but a 6.0 upgrade should grep for `JSONField` filter expressions.
  - `URLField` default scheme switched to `https`; project does not use `URLField` (only `EmailField`), so no impact.
- **Settings docstring rot.** The first 11 lines of `MetaGap/MetaGap/settings.py` still reference *"Django 2.1.2"* and link to `docs.djangoproject.com/en/2.1/`. Trivial cleanup along with the Django bump.

### VCF/Genomics Horizon

- **VCFv4.5** is the canonical specification per `samtools/hts-specs` (`VCFv4.5.tex`). `VCFv4.4.tex` is now in the historical-predecessors set. The active extension draft (`hts-specs/issues/767`) carries modified-base information in the genotype.
- The importer routes any unmapped `##` section into `SampleGroup.additional_metadata`, unmapped INFO/FORMAT keys into `Info.additional` / `Format.additional` (`models.py:288, 365-376`) — so 4.5 files won't error. They also won't be *understood*: 4.5's new reserved INFO keys (modified-base annotations, haplotype-linkage codes) become anonymous JSON.
- **pysam 0.23.3 wraps htslib 1.23.1**, which is 4.5-aware; bumping is the cheapest path to "we read 4.5 correctly" without authoring a parser update. Note: the pysam read-the-docs page sometimes lists htslib 1.18 in the 0.23.x bullet — that is the *initial* 0.23.0 wrap; the 0.23.3 release pulls 1.23.1.
- **vcfpy is still flagged as inactive** (Snyk advisor, 2026): no PyPI release in >12 months, sparse PR/issue activity, ≤10 contributors. Used only by `MetagapUserCode/merge_vcf/__init__.py:29` (lazy `_import_dependency` import). When cohort-merge meets a 4.5-only header we will need a fallback. **Pre-empting with `cyvcf2`** (cython + htslib, MIT, fastest of the three) **or a thin pysam-based merge** is the lower-risk path; `vcfpy`'s strength is mutating VCF in place, which `merge_vcf` does not do.
