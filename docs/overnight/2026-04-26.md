## Research Findings

### Django Updates & Deprecations

- **Django 5.1 has been EOL since 2025-12-31**; no further security fixes. Django 5.2 LTS (supported through 2028-04) is the recommended landing point. ([endoflife.date/django](https://endoflife.date/django))
- **Django 6.0 GA shipped 2025-12-03** — *not* an LTS — bringing Template Partials (`{% partialdef %}` / `{% partial %}`), built-in async **Tasks** framework, native CSP support (no more middleware shim), and a modernized Email API. These are post-5.2 wins, not blockers. ([Django 6.0 release notes](https://docs.djangoproject.com/en/6.0/releases/6.0/))
- **2026-04-07 security release** (Django 5.2.13 / 6.0.4 / 4.2.30): three CVE-tier fixes — ASGI underscore-header normalization (matches Daphne behavior), `GenericInlineModelAdmin` per-instance add permission validation on POST, admin changelist `list_editable` no longer accepts forged POST data to create instances. All low severity; 5.1.1 is missing every patch. ([Django security release](https://www.djangoproject.com/weblog/2026/apr/07/security-releases/))
- **`USE_L10N` was already removed in Django 5.0** (per the official deprecation timeline — *deprecated in 4.0, removed in 5.0*). The line `USE_L10N = True` at `MetaGap/MetaGap/settings.py:138` is therefore inert dead syntax on a 5.1 install — Django 5.x permanently treats `USE_L10N` as `True`. Delete the line as part of the Django bump.
- **Django 6.0 JSONField deprecations** to know about for the eventual 6.0 jump:
  - `django.contrib.postgres.fields.JSONField` will be removed (a stub stays for historical migrations).
  - `JSONField`-as-encoded-string-literal lookups will be removed.
  - Querying a top-level `JSONField` value with `None` will compile to `IS NULL`; use `JSONNull` to match a JSON `null`. We do use `JSONField` in `Info.additional`, `Format.payload`, `SampleGroup.additional_metadata`, `SequencingInstrument.additional_info`, `ReferenceGenomeBuild.additional_info`, `InputQuality.additional_metrics` — none use the deprecated string-literal pattern, but a 6.0 upgrade should grep for `JSONField` filter expressions.
  - `URLField` default scheme switched to `https` in 6.0; project does not use `URLField` (only `EmailField`), so no impact.
- The settings module's docstring still references *"Django 2.1.2"* and links to `docs.djangoproject.com/en/2.1/`. Trivial cleanup along with the Django bump.

### VCF/Genomics Horizon

- **VCFv4.5** has been the canonical samtools/hts-specs version since 2024-10-09 (`samtools/hts-specs/VCFv4.5.pdf`). 4.4 is officially superseded. The active draft (`hts-specs/issues/767`) extends the genotype to carry modified-base information.
- The importer routes any unmapped `##` section into `SampleGroup.additional_metadata`, unmapped INFO/FORMAT keys into `Info.additional` / `Format.additional` (`models.py:288, 365-376`) — so 4.5 files won't error. They also won't be *understood*: 4.5's new reserved INFO keys (modified-base annotations, haplotype-linkage codes) become anonymous JSON.
- **pysam 0.23.3 wraps htslib 1.23.1**, which is 4.5-aware; bumping is the cheapest path to "we read 4.5 correctly" without authoring a parser update.
- **vcfpy is now flagged as inactive** (Snyk advisor, 2026): no PyPI release in >12 months, no PR/issue activity in the last month, ≤10 contributors. Used only by `MetagapUserCode/merge_vcf/__init__.py:29` (lazy `_import_dependency` import) — when cohort-merge meets a 4.5-only header we will need a fallback. Pre-empting with `cyvcf2` or a thin `pysam`-based merge could be considered.
