### Section-key drift (concrete example)
YAML `reference_genome_build.build_name` aliases: `["name", "reference", "build"]`.
Python `METADATA_FIELD_ALIASES["reference_genome_build"]["build_name"]`: `["name", "reference", "build", "buildname"]`.
Same for `build_version` (Python adds `"buildversion"`). A VCF using `Buildname=` would parse correctly via the in-process parser but be ignored if the YAML loader path is exercised (e.g. by an integration test that overrides `config_path`).

## Research Findings

### Django Updates & Deprecations
**Django 5.2 (LTS, Apr 2025) net-relevant changes for this codebase:**
- `CompositePrimaryKey` — not directly applicable (no obvious composite-PK candidates in `models.py`; `AlleleFrequency` has a `UniqueConstraint` but `id` is fine), so the feature is a non-event for us.
- `shell` auto-imports models — small ergonomic win.
- PostgreSQL ≥ 14 required, MySQL switches to `utf8mb4` default — irrelevant on SQLite default but worth noting if any deployment uses MySQL.
- Deprecations that bite us:
  - `django.contrib.staticfiles.finders.find()` `all=` argument deprecated in favor of `find_all=`. We don't call this directly, but if any management command does, it'll start raising warnings on 5.2.
  - `request.user` / `request.auser()` fallback when `user is None` in `auth.login()` is deprecated. Search through `views.py` shows we call `login()` only via allauth, so likely safe, but worth a re-run on 5.2.
- Django 5.1 reaches **end of mainstream support** in Dec 2025 (per endoflife.date). 5.2 is LTS through 2028. Strong case for prioritizing the 5.1→5.2 jump separately from the 5.2→6.0 work.

### VCF/Genomics Horizon
- **VCF 4.5 not yet published.** Latest published spec is **4.4** (2022, samtools/hts-specs). GA4GH stewards the spec now. Our YAML config covers VCFv4.2 conventions; nothing in the importer breaks against 4.4, but new INFO/FORMAT field types added in 4.4+ (e.g. `Number=R`, structural variant additions) are not represented in `INFO_FIELD_MAP` / `FORMAT_FIELD_MAP` in `vcf_database.py`. They'd land in the `additional` JSON field today.
- **cyvcf2** (cython htslib wrapper, brentp) benchmarked **~6.9× faster than pysam** for VCF parsing in published peer-reviewed benchmarks. Drop-in replacement is non-trivial because we use `pysam.VariantFile.fetch()` and access `record.info`/`record.samples` heavily, but it's a credible perf lever if VCF imports become a hotspot. Not urgent — most users today import < 100MB VCFs.
- vcfpy upstream is showing low maintenance signals (no PyPI release in ~12 months per Snyk). `MetagapUserCode/merge_vcf/merging.py` depends on it; long-term we may want to migrate the merge tool to pysam or cyvcf2 to consolidate dependencies.

### CI Gaps
The current `.github/workflows/ci.yml` (read in full) does the bare minimum: `coverage run manage.py test` + threshold enforcement + `Unhandled metadata key` warning annotation. Concrete gaps:

1. **No linter / formatter.** No ruff, no black, no flake8, no isort. PRs can land with arbitrary style. Ruff is now the community default (per Astral / pre-commit ecosystem); a single `ruff check .` step adds ~3 s.
2. **No security scanning.** Neither `pip-audit` nor `safety` nor `bandit` runs. Given urllib3 CVE-2026-21441 and the Django 5.1 CVE chain, this is the cheapest immediate improvement.
3. **No pytest invocation.** Function-style tests in `app/tests/` and many in `MetagapUserCode/tests/` are never executed (Django's `manage.py test` only discovers `unittest.TestCase` subclasses). Adding a `pytest -q` step would surface this immediately — though it'll likely fail until the `test_vcf_database.py` references to non-existent `description` / `organization_profile` / `insert_buffer_size` fields are fixed (see Unused Code).
4. **No type checking.** No mypy / pyright. The codebase has type annotations throughout (`models.py`, services) but they're never validated.
5. **No `pip` cache** in `actions/setup-python@v5` — every CI run reinstalls all deps from scratch. Adding `cache: 'pip'` shaves ~30–60 s per run.
6. **`continue-on-error: true`** on the test step combined with a manual `if: steps.tests.outcome == 'failure'` re-fail at the bottom is fragile. Standard practice is to let the step fail naturally and run coverage/annotation steps with `if: always()`.
7. **Threshold enforcement re-runs `coverage report` three times** (once for summary, once for `MetagapUserCode/`, once for `app/`). Consolidating into a single invocation with `--include` would speed it up slightly.
8. **No matrix.** Only Python 3.11 is tested. Project pins `Python 3.11+` per requirements.txt comment, but no CI assurance against 3.12 / 3.13.

### Test Quality Notes
- **The pytest/Django split is the real story.** `app/tests/test_vcf_database.py`, `test_vcf_metadata.py`, `test_filters.py`, `test_filters_additional.py`, `test_views_additional.py`, `test_vcf_file_utils.py`, `test_locale_compiler.py` are written as pytest functions with `pytestmark = pytest.mark.django_db`. Django's test runner (`manage.py test`) discovers `unittest.TestCase` subclasses, not bare `def test_*` functions; so the actual executed test count is **154**, not the "320+" figure cited in `CLAUDE.md`. Run `pytest --collect-only` to see how many tests are silently dropped today.
- `test_import_data_view.py` is empty (see Unused Code). Real `ImportDataView` behavior is exercised by `test_views_import_export.py` and `test_integration_workflow.py`, but the dedicated module name implies regression coverage that isn't there.
- `test_signals.py` is 24 lines — small surface but probably adequate (the signal it tests, `OrganizationProfile` auto-creation, is one-shot).
- Happy-path bias spot-check: `test_vcf_importer.py` does include malformed-header VCF tests (`MALFORMED_HEADER_VCF`) and pysam-fallback warning assertions, so the importer is well-covered. The `_should_retry_with_inflated_copy` substring filter and `_inflate_gzip_to_temp` cleanup branch (noted earlier) are the gaps.
- `test_locale_compiler.py` uses pytest functions and is therefore not run in CI — anything it asserts about gettext compilation is currently un-enforced.

## Suggestions
Ranked by ratio of value to effort.

1. **Add a `pytest` step to CI** (or migrate the orphan pytest tests to `unittest.TestCase`). This is the single highest-leverage change — there are likely hundreds of un-run assertions in the suite. After doing so, expect failures in `test_vcf_database.py` (broken references) and reconcile.
2. **Delete dead code from `app/services/vcf_database.py`** — `get_or_create_sample_group`, `convert_to_python_type`, `extract_*_field_metadata`. They are not called by production and the `get_or_create_sample_group` body references model fields that don't exist; keeping them is actively misleading.
3. **Bump Django to 5.2.13 (LTS)** — gets multiple 2026 CVE patches in one move and aligns with the 3-year support window. Run the test suite (and a fresh `pytest`) on a feature branch first; the deprecations listed above are non-breaking but produce log noise.
4. **Bump urllib3 ≥ 2.6.3 (or remove `requests` from `requirements.txt` entirely)** — the latter is preferable since nothing in the project imports `requests`. Same for `beautifulsoup4` and `docutils`. Removing three packages eliminates the urllib3 CVE-2026-21441 finding without any code change.
5. **Add `pip-audit` and `ruff` steps to the CI workflow.** Pip-audit catches future urllib3-style CVEs automatically; ruff enforces consistent style and import ordering. ~10 lines of YAML.
6. **Pick one source of truth for `METADATA_SECTION_MAP` / `METADATA_FIELD_ALIASES`** — either delete the in-code copies in `vcf_metadata.py:183-366` and have `vcf_file_utils.py` use `load_metadata_configuration()` like the rest of the importer, or delete the YAML and document Python as canonical. Right now `buildname`/`buildversion` aliases exist only in Python and would silently be dropped if anyone refactored to YAML-only.
7. **Pin `coverage` in `requirements.txt`.** It is currently installed only by the CI `pip install ... coverage` line, so local developers can't run the same coverage command CI does. A line in requirements.txt + a one-line README note avoids the kind of "guard prevents install" friction this report ran into.
8. **Add an `actions/setup-python@v5` `cache: 'pip'` line and consolidate the threshold-enforcement coverage report invocations.** Small CI speedup, free.
